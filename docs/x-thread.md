# X thread draft

1/
我把本机 386 次 agent 会话的日志全部解开数了一遍。

23.8 亿 prompt token 里，98.6% 是模型已经看过的上下文在被反复重发，只有 1.2% 是新内容。

最贵的一轮，单独吃掉 4,000 万 token。

2/
先说个坑：日志里那个 `inputTokens` 字段，只是**未命中缓存**的输入。

真实上下文大小 = `inputTokens + cacheReadTokens`。

我第一版拿它当上下文大小，缓存一失效就造出 65 万 token 的假跳变，工具归因表里 bash 被算成 557% 的账单。

3/
换成 prompt token 口径后，每一轮都能严格分解：

carried = 重发的上下文
fresh = 这一步新增的内容

最贵的 10% 的回合，吃掉全部处理的 67.5%；中位数只有 27 万 token。

成本不是均匀分布的，它集中在你跑得最久的那几个回合里。

4/
工具归因（含重读放大）：bash 39.0%、read 11.1%，其余每一项都不到 4%。

原因很直接：bash 的输出长度没有上限。一次 `find`、一次构建日志，可能几千行，然后每一步都重新交一遍。

同一个文件在一次会话里被打开 40 次、29.5 万字符。

5/
还有个隐藏账单：825 次缓存未命中，等于把整段历史按全价重买了一遍。

它们集中在改系统提示、换模型、压缩历史的那几步——功能上都合理，成本上都是重付。

6/
结论：agent 的成本不在输出，在输入的重复里。

输出只占 0.6%。

下一步该做的不是更聪明的提示词，是给 agent 一个"上下文预算"的概念：像内存一样，知道谁在占、占了多少、什么时候该回收。

7/
工具开源了，零依赖，Node 24：

npm i -g dsh-tracer
dsh-trace scan ~/.dsh/sessions --html scan.html

386 份语料扫一遍 2 秒，报告是单文件 HTML，断网能开。
